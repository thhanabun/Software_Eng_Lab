# Lab 2 Sprint Engineering Specification

Version: 1.0 (approved before implementation) · Sprint: Lab 2 · Branch flow: `feature/lab2-*` → `lab2-staging` → `main`

## 1. Sprint Goal

Deliver the Requester-facing TokTickIT ticketing MVP: a Development Requester can select a temporary testing identity, create a validated IT support ticket with a backend-generated official Ticket Number, find and inspect their own tickets through search/filter/sort/pagination, and manage permitted attachments (upload, download, soft removal) — all inside a reusable, responsive Zen Green UI foundation that later labs build on.

## 2. Stakeholder Request Interpretation

In our own words: the IT department needs a real, professional intake experience for end users. A Requester describes a problem (summary + description), classifies it (category + related system), sets a requested priority, attaches evidence, and submits. The system assigns the official Ticket Number — never the client. Afterwards the Requester must be able to locate, inspect, and manage **their own** tickets and attachments; one Requester must never see another's data. Because real login arrives in Lab 3, this sprint ships a clearly-labelled Development Requester selector as a testing mechanism only. The UI work also establishes the Zen Green visual system and reusable component conventions (form, list, badge, validation, loading, empty, error, responsive layout) for all future screens.

## 3. Scope

### Included
- Development Requester Selection screen (temporary "login") and requester context behavior
- Create Ticket (API + UI + validation + duplicate-submission prevention)
- My Tickets (ownership-scoped list with search, filters, sorting, pagination)
- Requester Ticket Detail (read-only view mode)
- Attachment lifecycle: upload, metadata listing, download, soft removal with reason
- Zen Green theme tokens, reusable components, application shell + navigation
- Responsive behavior at desktop / tablet / mobile
- Data model + idempotent seed + migration for Lab 2 increment
- Automated tests: unit, API, UI component, UI style, responsive, E2E
- Spec/test/UI/API documentation in `docs/lab-02/`

### Excluded
- Authentication and security: login, logout, passwords, hashing, sessions, tokens, real role-based authorization (the selector is testing-only)
- IT Staff workflow: staff dashboard/queue, claiming, reassigning, IT Priority changes
- Collaboration and work tracking: Public Comments, Internal Notes, Actions Taken
- Ticket lifecycle after creation: any status change beyond the initial `NEW` (resolve, close, reopen, cancel)
- Administration: user/role/reference-data management screens

## 4. Functional Requirements

- FR-01: Select one active Development Requester from a dropdown loaded from PostgreSQL and continue into the app.
- FR-02: Display the current Requester in the application shell with a working Change Requester action.
- FR-03: Create a ticket with Category, Related System, Summary, Requested Priority, Description, and optional attachment selection; validate on client and server.
- FR-04: Generate the official Ticket Number (`TKT-YYYYMMDD-####`) on the backend and display it on the success state.
- FR-05: List the selected Requester's own tickets with search, category/status/priority filters, sorting, and pagination.
- FR-06: Open the Requester Ticket Detail screen showing read-only ticket information.
- FR-07: Upload a permitted attachment to an owned existing ticket.
- FR-08: List attachment metadata for a ticket, including soft-removed entries.
- FR-09: Download an active attachment.
- FR-10: Soft-remove an owned attachment with confirmation and required reason.
- FR-11: Provide loading, empty, no-results, and failure states on all data-driven screens.
- FR-12: Render all screens responsively with the Zen Green theme and keyboard-accessible controls.

## 5. Business Rules

- BR-01: The official Ticket Number is generated by the backend, is unique, and uses the format `TKT-YYYYMMDD-####` (date prefix + zero-padded daily sequence).
- BR-02: A new Ticket begins with Current Status `NEW`; Lab 2 performs no status transitions.
- BR-03: Lab 2 uses a Development Requester selector instead of login. The selected identity is a testing mechanism only and is not authentication.
- BR-04: Ticket Number and Ticket Date are system-generated, read-only, and exist only after successful creation.
- BR-05: Categories, Related Systems, and active Requesters are loaded from PostgreSQL — never hardcoded in the client.
- BR-06: The selected Requester is persisted client-side (localStorage key `toktickit.requesterId`) and sent as the `X-Requester-Id` header on every requester-scoped API call.
- BR-07: Changing the Requester reloads all requester-specific data; nothing from the previous Requester remains visible.
- BR-08: A Requester can only view and manage their own tickets and attachments. Ownership is enforced server-side on every endpoint; non-owned resources are answered as not found (no existence leakage).
- BR-09: Ticket Summary is required, trimmed, 1–120 characters after trimming. Description is required, trimmed, 1–2000 characters after trimming.
- BR-10: Requested Priority is required and one of `LOW`, `MEDIUM`, `HIGH`, `URGENT`.
- BR-11: Validation runs on both client and server; the server is authoritative and returns field-level details.
- BR-12: Duplicate submission is prevented by disabling the Submit button (busy state) while the request is in flight.
- BR-13: When ticket creation fails, all entered form values are preserved and a safe error message is shown.
- BR-14: Ticket list defaults: sorted by `createdAt` descending, page 1, pageSize 10. Secondary sort is always `ticketNumber` descending for stable ordering.
- BR-15: Search is case-insensitive substring matching over Summary and Description.
- BR-16: Permitted page sizes are {5, 10, 25}. Invalid page, pageSize, filter value, or sort value returns 400 with a safe message; unknown query parameters are ignored.
- BR-17: Attachments allow only JPG/JPEG, PNG, WEBP, PDF; maximum 5 MB per file; maximum five active attachments per ticket.
- BR-18: Uploaded files are stored on the server at `server/uploads/<uuid>.<ext>` (gitignored directory, server creates it at startup); the original filename is preserved in metadata only.
- BR-19: Attachment removal is soft: `removedAt` + `removalReason` are recorded; metadata remains visible in listings; removed files can never be downloaded or previewed (download returns 410).
- BR-20: Soft removal requires an explicit confirmation and a removal reason (1–200 characters after trimming).
- BR-21: Only the owning Requester may upload, download, or soft-remove a ticket's attachments.
- BR-22: Ticket creation and attachment upload are separate steps: the ticket is created first (201), then each selected file is uploaded. If any upload fails, the ticket is kept, the failures are reported per file, and the user can retry from Ticket Detail (compensation strategy — no silent loss, no orphaned uploads).
- BR-23: Inactive Requesters are excluded from the selector and cannot create tickets (server rejects with 400). Their **existing** tickets/attachments remain readable via the API (audit retention); only writes are blocked.
- BR-24: My Tickets distinguishes an empty state (Requester has no tickets at all) from a no-results state (filters/search excluded everything).
- BR-25: A non-existent or non-owned ticket id returns 404 with a safe message.
- BR-26: All API errors use the safe error shape; no stack traces, SQL, or internal paths are exposed. Unexpected failures return 500.
- BR-27: Seed data is idempotent (safe to re-run without duplicates, and never re-activates a manually deactivated Requester/Related System) and contains: the 4 required categories — **Account and Access, Hardware, Software, Network** — at least 6 related systems (Email, Campus Wi-Fi, VPN, LEB2 App, Grade Submission App, Printer, Corporate Laptop), at least 4 active requesters, and at least 1 inactive requester.
- BR-28: Lab 3 transition: the `X-Requester-Id` context mechanism will be replaced by real authentication without changing the ticket/attachment ownership model (tickets keep their requester FK).

## 6. UI Specification Summary

Zen Green theme tokens (full detail in `ui-spec.md`): primary `#006B3C` (header, primary actions), secondary `#0B7A46` (active tabs, focus, links, hover), pale `#EAF6EF` (selected/success/subtle), background `#F5F7F6`, white surfaces with subtle border/shadow, charcoal-green text, read-only fields shaded `#F1F4EF`, dark-red errors below fields, amber warnings, green success that never relies on color alone.

Screens and routes: Requester Selection (`/select-requester`), Create Ticket (`/tickets/new`), My Tickets (`/tickets`), Ticket Detail (`/tickets/:id`). Application shell: TokTickIT identity, My Tickets + Create Ticket navigation with active-page indication, current Requester display, Change Requester action, responsive mobile navigation. No selected Requester → redirect to Selection.

Component rules: labels above controls; red asterisk on required fields (in addition to messages); consistent input heights; visible button text; accessible icon-only controls; visually distinct disabled controls; visible focus rings; busy/disabled Submit; field-level validation placement; success state shows the generated Ticket Number and next action. My Tickets: desktop table ↔ mobile cards with Ticket Number, Summary, Category, Status badge, Last Updated. Badges: Requested Priority and Current Status styles defined in ui-spec.md.

Responsive: desktop ≥992px centered max-width multi-column; tablet 768–991px two-column; mobile <768px stacked with touch-friendly buttons and no horizontal scrolling.

## 7. Data Changes

New/updated Prisma models (PostgreSQL):

| Model | Key fields | Notes |
|---|---|---|
| `Category` | id, name (unique), createdAt | existing from Lab 1 |
| `RelatedSystem` | id, name (unique), active, createdAt | new |
| `RequesterUser` | id, name, email (unique), active, createdAt | new; temporary dev identity |
| `Ticket` | id, ticketNumber (unique), requesterId FK, categoryId FK, relatedSystemId FK, summary, description, requestedPriority enum, currentStatus enum default NEW, createdAt, updatedAt | new |
| `Attachment` | id, ticketId FK, originalName, storedName (unique), mimeType, sizeBytes, uploadedAt, removedAt?, removalReason? | new; soft removal fields |

Enums: `RequestedPriority { LOW MEDIUM HIGH URGENT }`, `TicketStatus { NEW }`.

Relationships: Requester 1—N Tickets; Ticket 1—N Attachments; Category 1—N Tickets; RelatedSystem 1—N Tickets.

Indexes/constraints: unique on ticketNumber, requester email, category name, related system name, and attachment storedName; `@@index([requesterId, createdAt(sort: Desc)])` for the owned list default query; `@@index([currentStatus])` and `@@index([categoryId])` for filters; `@@index([ticketId])` on Attachment because Postgres does not auto-index FK columns and every attachment listing/limit check filters by it. Soft removal is represented by nullable `removedAt`/`removalReason` (no row deletion; partial uniqueness stays on storedName).

**Justified design decision (required by labsheet):** attachment files live on disk under `server/uploads/` while only metadata lives in PostgreSQL. Rationale: binary files bloat the database, complicate backups, and make streaming downloads awkward; metadata-only rows keep queries fast and let soft removal work by flipping two columns while the file stays on disk (never served once removed). The UUID stored name prevents filename collisions and path traversal; the original name is preserved for display/Content-Disposition only.

Migration: one `prisma migrate dev` increment named for the Lab 2 models. Seed extends the existing idempotent seed script.

## 8. API Contract

Detailed contract in `api-spec.md`. Summary:

| Endpoint | Method | Purpose | Success | Key errors |
|---|---|---|---|---|
| `/api/health` | GET | health (Lab 1) | 200 | 503 |
| `/api/categories` | GET | categories (Lab 1) | 200 | 500 |
| `/api/related-systems` | GET | active related systems | 200 | 500 |
| `/api/requesters` | GET | active development requesters | 200 | 500 |
| `/api/tickets` | POST | create ticket | 201 | 400 |
| `/api/tickets` | GET | owned list (search/filter/sort/page) | 200 | 400, 404 |
| `/api/tickets/:id` | GET | owned detail | 200 | 400, 404 |
| `/api/tickets/:id/attachments` | POST | upload attachment (multipart) | 201 | 400, 404, 409, 413, 415 |
| `/api/tickets/:id/attachments` | GET | attachment metadata list | 200 | 400, 404 |
| `/api/attachments/:id` | GET | single attachment metadata | 200 | 400, 404 |
| `/api/attachments/:id/download` | GET | download active file | 200 | 400, 404, 410 |
| `/api/attachments/:id` | DELETE | soft removal (reason required) | 200 | 400, 404, 409 |

Ownership: `X-Requester-Id` header is required on all `/api/tickets*` and `/api/attachments*` endpoints; missing/invalid → 400, unknown requester → 404, non-owned resource → 404.

## 9. Acceptance Criteria

- AC-01: Given valid ticket data, when the Requester submits the form, then one Ticket is saved and the official Ticket Number is returned (201) and displayed.
- AC-02: Given no Development Requester is selected, when the user opens any ticket screen, then the Requester Selection screen is shown.
- AC-03: Given Requester B is selected, when a Ticket belonging to Requester A is requested, then no ticket data is returned (404).
- AC-04: Given the Create Ticket screen, then Ticket Number and Ticket Date are read-only and have no value before successful creation.
- AC-05: Given a successful submission, then the success state shows the generated Ticket Number and a next action (view ticket / create another).
- AC-06: Given missing Summary or Description, when submitting, then field-level messages appear and no ticket is saved.
- AC-07: Given invalid Category, Related System, or Priority values, when submitting, then the API returns 400 with safe field-level errors.
- AC-08: Given a submission in flight, then the Submit button is busy/disabled and a second click cannot duplicate the request.
- AC-09: Given the API fails during creation, then a safe error is shown and all form values are preserved.
- AC-10: Given the Create Ticket screen loads, then Categories, Related Systems, and the Requester field come from the database/selected context.
- AC-11: Given My Tickets, then only the selected Requester's tickets are returned (ownership enforced server-side).
- AC-12: Given a search term, then matching tickets by Summary or Description are returned case-insensitively.
- AC-13: Given category/status/priority filters, then results are narrowed accordingly.
- AC-14: Given no sort parameter, then results are ordered by createdAt descending with ticketNumber descending as secondary sort; documented sort options work.
- AC-15: Given pagination parameters, then the correct page slice plus metadata (page, pageSize, totalItems, totalPages) is returned; permitted sizes are {5,10,25}.
- AC-16: Given invalid query parameters, then the API returns 400 with a safe message.
- AC-17: Given the Requester has no tickets, then the empty state shows; given filters exclude all results, then the distinct no-results state shows.
- AC-18: Given Requester A's list is visible, when switching to Requester B, then A's tickets disappear and B's data loads.
- AC-19: Given the owner opens Ticket Detail, then all ticket information renders read-only.
- AC-20: Given a valid permitted file, when uploaded to an owned ticket, then 201 is returned and the attachment appears in the list.
- AC-21: Given a wrong file type / oversize file / sixth active file, when uploading, then 415 / 413 / 409 is returned with a safe message and nothing is stored.
- AC-22: Given an active attachment, when downloading, then the original filename and correct content type are served.
- AC-23: Given the remove confirmation with a reason, when confirmed, then the attachment is soft-removed (metadata retained, reason shown) and download returns 410.
- AC-24: Given the seed includes an inactive Requester, then that Requester does not appear in the selector and cannot create tickets.
- AC-25: Given the selector screen, then loading, empty, and API-failure states render correctly.
- AC-26: Given desktop / tablet / mobile viewports, then all screens remain usable with no clipping, overlap, or horizontal scrolling.
- AC-27: Given the implemented screens, then Zen Green tokens/classes conform to ui-spec.md (verified by style assertions).
- AC-28: Given keyboard-only operation, then all controls are reachable with visible focus indicators.
- AC-29: Given Requester B's context, when requesting Requester A's attachment directly, then access is rejected.
- AC-30: Given a ticket is created with selected attachments and one upload fails, then the ticket is kept, the failed file is reported, and the user is directed to retry from Ticket Detail.

## 11. Assumptions and Decisions

- AD-01: Ticket Number format `TKT-YYYYMMDD-####` — daily sequence zero-padded to 4 digits; unique constraint + retry loop (max 5 attempts) on collision.
- AD-02: Identity context = `X-Requester-Id` header from localStorage selection; deliberately simple so Lab 3 can swap in real auth without schema churn.
- AD-03: Attachments stored on local disk `server/uploads/` (adequate for MVP; object storage is a post-course concern).
- AD-04: `react-router-dom` handles navigation and active-page indication.
- AD-05: Downloading a removed attachment returns **410 Gone** (semantically explicit; documented in api-spec.md).
- AD-06: Page sizes limited to {5, 10, 25}, default 10 — keeps server queries predictable.
- AD-07: Summary ≤ 120 chars, Description ≤ 2000 chars (after trim) — justified by list readability and storage sanity.
- AD-08: Playwright for E2E tests and responsive screenshots into `artifacts/lab-02/screenshots/`.
- AD-09: Priority ordering for sort is enum severity order URGENT > HIGH > MEDIUM > LOW.
- AD-10: The date part of the Ticket Number uses server-local date (single-server MVP; containers share timezone).
- AD-11: Create flow is two-step (create ticket → upload files sequentially) so a failed upload never blocks or rolls back a valid ticket (BR-22).
- AD-12: Existing Lab 1 `/api/categories` endpoint is reused unchanged for the Create Ticket category dropdown.
