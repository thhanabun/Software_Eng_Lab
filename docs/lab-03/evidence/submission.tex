\subsection*{Rendered specification.md --- full contract text}
Below is the complete approved \texttt{specification.md} (all 11 required sections, verbatim content rendered as LaTeX).

\subsubsection*{1. Sprint Goal}
Replace the Development Requester selector with secure cookie-based authentication. Introduce three roles (REQUESTER, IT\_STAFF, ADMINISTRATOR). Implement IT Staff ticket queue and detail operations (claim, assign, priority, status transitions, comments, notes). Add minimalist Administrator user management. Preserve Lab 2 Requester flows under authenticated identity. Maintain Zen Green design language.

\subsubsection*{2. Stakeholder Request Interpretation}
The temporary Requester selector was useful for development, but the system now needs real users. Replace it with secure login. Administrators need a simple User Management screen where they can view users, create an account, assign one role, update basic account information, activate or deactivate accounts, and set initial passwords. IT Staff need a shared ticket queue with operations to claim, assign, set priority, change status, post public comments, and write internal notes. Continue using the Zen Green design language and reusable components established in Lab 2.

\subsubsection*{3. Scope}
\paragraph*{Included}
\begin{itemize}
\item Cookie-session authentication: login, logout, current user, mandatory first-login password change
\item Server-side role authorization (REQUESTER / IT\_STAFF / ADMINISTRATOR) + ownership checks
\item Migration RequesterUser $\to$ User model preserving ticket/attachment ownership
\item Requester regression: identical Lab 2 functions under authenticated identity + Public Comments + Resolved indication
\item IT Staff Ticket Queue (search/filter/sort/pagination)
\item IT Staff Ticket Detail (claim/assign/priority/status/comments/notes/download)
\item Administrator User Management (list/search/create/edit/reset/deactivate)
\item Data model increment + idempotent seed + migration evidence
\item Automated tests: unit, API, UI, style, security/authorization, migration/regression, E2E
\end{itemize}

\paragraph*{Excluded}
\begin{itemize}
\item Email invitations, password-reset email, MFA, social login, SSO
\item Self-registration and Requester-created accounts
\item Actions Taken by IT Staff (deferred to Lab 4)
\item SLA calculation, escalation rules, notification services, dashboards
\item Multi-tenant organizations, departments, customer administration
\item Account unlocking / lockout (no lockout in Lab 3)
\item User deletion (deactivation only), bulk operations, import/export
\end{itemize}

\subsubsection*{4. Functional Requirements (FR-01 through FR-17)}
\begin{itemize}
\item FR-01: Sign in with email + password; establish server session delivered as httpOnly cookie.
\item FR-02: Force users with initial password through a Change Password screen before any normal screen is reachable.
\item FR-03: Show authenticated user's name + role in the shell; provide Logout that invalidates session.
\item FR-04: Expose current user to client (\code{GET /api/auth/me}) for guards and role navigation.
\item FR-05: Create/list/detail/attachments behave exactly as Lab 2, with ownership derived from session identity.
\item FR-06: Post Public Comments on owned tickets.
\item FR-07: Indicate ``Problem Appears Resolved'' on owned tickets in permitted statuses.
\item FR-08: Browse shared Ticket Queue with search, filters, sorting, pagination; open any ticket's detail.
\item FR-09: Claim a ticket (self-assign) or assign/reassign it to an active IT Staff or Administrator.
\item FR-10: Set IT Priority (initially copies Requested Priority).
\item FR-11: Move tickets through permitted status transitions only (matrix BR-17).
\item FR-12: Post Public Comments and write Internal Notes on any ticket.
\item FR-13: List users (Name, Email, Role, Status, Edit action) with search and role filter.
\item FR-14: Create a user with name, email, role, activation state, and initial password.
\item FR-15: Edit a user's name, email, role, and activation state.
\item FR-16: Issue a new initial password (account returns to must-change state).
\item FR-17: Enforce safety rules: no self-deactivation, never remove last active Administrator, unique emails.
\end{itemize}

\subsubsection*{5. Business Rules (BR-01 through BR-30)}
\begin{itemize}
\item BR-01: Only an active user with valid credentials may authenticate.
\item BR-02: Must-change user cannot enter normal application until valid new password saved.
\item BR-03: Authenticated user identity (not client-supplied id) determines ownership.
\item BR-04: Public Comments visible to Requester, IT Staff, Administrator. Internal Notes visible only to IT Staff and Administrator.
\item BR-05: Requester may indicate ``problem appears resolved'' but cannot formally set Resolved or Closed.
\item BR-06: Failed logins return identical generic 401 with no account-enumeration signal.
\item BR-07: Inactive account with valid credentials $\to$ 403 with deactivated message.
\item BR-08: Passwords stored as bcrypt hashes (cost 12), never plaintext. Hashes never leave the server.
\item BR-09: New/initial passwords: 8--72 chars, at least one letter and one digit; confirmation must match; new password must differ from current/initial.
\item BR-10: Sessions: opaque random token in cookie \code{toktickit\_session} (httpOnly, SameSite=Lax, Secure in production), server-side Session row with 8-hour absolute expiry (30 minutes for pending-change sessions).
\item BR-11: \code{GET /api/auth/me} returns only safe identity fields (id, name, email, role, active, mustChangePassword).
\item BR-12: All Lab 2 ownership rules persist. \code{X-Requester-Id} removed entirely.
\item BR-13: Attachment rules unchanged (types, 5 MB, 5-active limit, soft removal).
\item BR-14: Each ticket has zero or one primary owner (active IT Staff or Administrator). Unassigning active-work ticket $\to$ NEW.
\item BR-15: Requested Priority immutable after creation. IT Priority initialized as copy; only IT Staff/Admin may change.
\item BR-16: Only IT Staff/Administrator may change status, and only along the permitted transition matrix.
\item BR-17: \textbf{Transition Matrix:} NEW$\to$\{OPEN,CANCELLED\}; OPEN$\to$\{IN\_PROGRESS,WAITING\_FOR\_REQUESTER,CANCELLED\}; IN\_PROGRESS$\to$\{WAITING\_FOR\_REQUESTER,RESOLVED,CANCELLED\}; WAITING\_FOR\_REQUESTER$\to$\{IN\_PROGRESS,CANCELLED\}; RESOLVED$\to$\{CLOSED,REOPENED\}; CLOSED$\to$\{REOPENED\}; REOPENED$\to$\{IN\_PROGRESS,CANCELLED\}; CANCELLED = terminal.
\item BR-18: Requester resolved-indication allowed only when status in \{OPEN, IN\_PROGRESS, WAITING\_FOR\_REQUESTER\} and ticket is owned by caller. Sets flag + auto public comment. Never changes status.
\item BR-19: Both comments and notes are append-only. Author + server timestamp recorded by backend.
\item BR-20: Body required, trimmed, 1--2000 chars.
\item BR-21: Bodies render as plain text. Requester comment/note on non-owned tickets $\to$ 404; requester hitting Internal Note endpoints $\to$ 403.
\item BR-22: Comment/note creation on CANCELLED tickets is rejected (400). CLOSED tickets still accept comments.
\item BR-23: Create requires name (1--100), valid unique email, one of REQUESTER/IT\_STAFF/ADMINISTRATOR, and initial password meeting BR-09. Account starts with mustChangePassword=true.
\item BR-24: Edit may change name, email (still unique), role, active flag. Role change never leaves zero active Administrators.
\item BR-25: Administrator cannot deactivate their own account (400).
\item BR-26: System must always retain $\ge$1 active Administrator.
\item BR-27: Issuing new initial password sets mustChangePassword=true. Passwords never returned in any response.
\item BR-28: No user deletion anywhere -- deactivation only.
\item BR-29: All APIs keep Lab 2 safe-error shape and codes, plus 401/403/422 for authentication/authorization violations.
\item BR-30: Staff may filter by status, owner, priority; sort by any displayed column; paginate with server-set defaults.
\end{itemize}

\subsubsection*{6. Data Model Requirements}
\begin{itemize}
\item \textbf{User} fields: id (cuid), name, email (unique), role, active, mustChangePassword, passwordHash, createdAt, updatedAt.
\item \textbf{Session} fields: id (cuid), token (unique, indexed), userId (FK), expiresAt, createdAt.
\item \textbf{Ticket} adds: ownerId (optional FK User), itPriority (optional), resolvedAt (optional). Keeps all Lab 2 fields.
\item \textbf{Comment} adds: type (PUBLIC $\mid$ INTERNAL), authorId (FK User).
\item RequesterUser table dropped. Seed creates demo Users: requester@test.com, staff@test.com, admin@test.com.
\end{itemize}

\subsubsection*{7. Acceptance Criteria}
\begin{enumerate}[label=\arabic*.]
\item Admin login $\to$ Dashboard with Tickets (readonly), Staff Queue, User Management.
\item Requester login $\to$ same Lab 2 Dashboard, Create Ticket, My Tickets, Ticket Detail, Attachments, Public Comments, ``Problem Appears Resolved''.
\item Staff login $\to$ Tickets (readonly) and Staff Queue (shared).
\item Unauthorized access $\to$ redirect to Login. Wrong password $\to$ inline error. Inactive account $\to$ blocked.
\item User Management CRUD works with search, role filter, safe error messages.
\item Status transitions follow the approved matrix; illegal moves produce 400.
\item Seed users login with documented initial passwords; must-change flows correctly.
\end{enumerate}

\item \textbf{Staff Queue:} table with search, status/owner/priority filters, sortable columns, pagination.
\item \textbf{Staff Detail:} read-only ticket info + Assign/Reassign, Priority, Status transition dropdown + Confirm, Public Comment + Internal Note, Download attachment.
\item \textbf{User Management (Admin):} table with search + role filter; actions: Create, Edit, Reset Password, Activate/Deactivate.
\item \textbf{Create User:} name, email, role dropdown, activation toggle, initial password.
\item \textbf{Edit User:} name, email, role, activation; separate Reset Password button.
\end{itemize}

\subsubsection*{11. Assumptions and Constraints}
\begin{itemize}
\item PostgreSQL 16 via Docker Compose (port 5432).
\item Seed data provides three demo users with documented initial passwords.
